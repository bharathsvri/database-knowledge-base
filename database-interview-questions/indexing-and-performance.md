## Beginner Level

### Q1: How does a B-Tree index work internally?
#### Short Interview-Ready Answer
"A B-Tree (Balanced Tree) is a self-balancing, multi-way search tree where all leaf nodes reside at the exact same depth. Internal nodes store keys and child pointers that guide searches, while leaf nodes contain sorted keys alongside physical tuple identifiers (TIDs / CTIDs) pointing to actual rows on disk. Leaf nodes are linked as a doubly-linked list, allowing both $O(\log N)$ exact lookups and efficient sequential range scans."

## Intermediate Level

### Q2: What is a Covering Index (Index-Only Scan)?
#### Short Interview-Ready Answer
"A covering index is an index that includes all columns referenced by a query (in `SELECT`, `WHERE`, `JOIN`, and `GROUP BY`). When a query hits a covering index, the database engine executes an **Index-Only Scan**, satisfying the query entirely from the index leaf pages in memory without having to perform expensive random disk I/O to fetch table heap pages."

```sql
-- PostgreSQL Covering Index using INCLUDE clause:
CREATE INDEX idx_orders_covering 
ON orders (customer_id, order_date) 
INCLUDE (total_amount, status);

-- This query runs as an Index-Only Scan:
SELECT total_amount, status 
FROM orders 
WHERE customer_id = 450 AND order_date >= '2026-01-01';
```

### Q3: What is the "Leftmost Prefix Rule" in composite indexes?
#### Short Interview-Ready Answer
"In a multi-column composite index `CREATE INDEX idx_abc ON users (col_a, col_b, col_c)`, the B-Tree sorts keys hierarchically by `col_a` first, then `col_b`, then `col_c`. 

The query optimizer can only utilize the index if the query filters on the leftmost column:
- `WHERE col_a = ?` $\to$ **Index Used**
- `WHERE col_a = ? AND col_b = ?` $\to$ **Index Used**
- `WHERE col_b = ? AND col_c = ?` $\to$ **Index NOT Used** (Full table scan required)"

## Advanced Level

### Q4: What is the difference between `EXPLAIN` and `EXPLAIN ANALYZE`?
#### Short Interview-Ready Answer
"`EXPLAIN` prints the query execution plan generated by the optimizer along with estimated costs and estimated row counts **without running the query**. `EXPLAIN ANALYZE` **actually executes the query**, displaying both the optimizer's estimates AND the real execution time, actual row counts, loop iterations, memory used, and disk spills."

> [!WARNING]
> Running `EXPLAIN ANALYZE DELETE FROM orders WHERE status = 'PENDING'` will **actually delete** matching rows! Wrap in a transaction and rollback when testing mutations:
> ```sql
> BEGIN;
> EXPLAIN ANALYZE DELETE FROM orders WHERE status = 'PENDING';
> ROLLBACK;
> ```

## Senior Engineer Level

### Q5: What causes Table and Index Bloat in PostgreSQL, and how does MVCC contribute?
#### Short Interview-Ready Answer
"In PostgreSQL's Multi-Version Concurrency Control (MVCC), when a row is updated or deleted, the old tuple is not overwritten or physically removed in-place. Instead, it is marked as dead by updating its `xmax` transaction header. 

Table and index bloat occur when dead tuples accumulate faster than `autovacuum` can reclaim them. Bloat is caused by:
1. Long-running transactions or uncommitted transactions holding old snapshots, blocking autovacuum from freezing or vacuuming dead tuples.
2. Large bulk UPDATE/DELETE batches.
3. Abandoned replication slots retaining old WAL and catalog snapshots.

*Mitigation:* Tune autovacuum scale factors (`autovacuum_vacuum_scale_factor = 0.05`), use `pg_repack` for online bloat removal without locking tables, and enforce `idle_in_transaction_session_timeout`."
